# 流程 14：最大可持续压力测试计划

## 1. 目标与定义

最大可持续吞吐：在冻结的硬件、容器资源、数据量和配置下，某一指定场景以候选 RPS 连续运行 30 分钟后，仍满足本流程 SLO 的最高 RPS。

每个结果必须同时记录实际活跃 VU 数。结果只适用于当前冻结环境，不得外推为生产容量或系统唯一“最大并发数”。

## 2. 固定入口与安全边界

所有压测请求必须经过：

`k6 → Nginx → Gateway → 微服务`

统一入口为：

`http://127.0.0.1:8088`

压测数据必须使用 `PERF14-` 前缀；不得影响非 `PERF14-` 数据。Redis 热点库存仅用于快速过滤，MySQL 条件更新仍是防超卖的最终边界；Outbox 是最终一致性机制，不是分布式强一致事务。

## 3. 环境冻结项

每个结果批次必须记录：

- Git commit、镜像标签和 Docker / Docker Compose 版本；
- 主机 CPU、内存、操作系统与 k6 版本；
- 每个容器的 CPU、内存限制及健康状态；
- Nacos Data ID、Group、修改时间和 MD5；
- 测试数据量、专用 MEMBER、商品和 SKU；
- 压测机位置：本机或第二台机器。

环境、镜像、Nacos 配置、容器资源或测试数据变化后，必须新建结果批次，不得横向比较旧结果。

## 4. 场景

| 编号 | 场景 | 目标 |
| --- | --- | --- |
| P1 | 热缓存商品详情 | 最大可持续吞吐 |
| P2 | 商品关键词搜索 | 最大可持续吞吐 |
| P3 | 冷缓存或缓存失效回源 | 退化能力 |
| P4 | 已登录购物车读写 | 最大可持续吞吐 |
| P5 | 热点库存下单 | 最大安全突发并发 |
| P6 | 浏览与搜索混合流量 | 30–60 分钟稳定性 |
| P7 | dev Gateway 限流 | 限流保护回归 |

P5 的订单确认后会持续占用库存；仅在有限专用库存范围内测量安全突发能力，不称为最大可持续下单 TPS。

## 5. 加压方法

采用 k6 到达率模型。每个场景按 10 RPS 预热 5 分钟开始，随后依次执行 20、40、80、160 RPS，每阶段 10 分钟，并持续翻倍直至瓶颈。

首个失败阶段出现后，在最后通过阶段与首次失败阶段之间二分定位；候选最高 RPS 必须再连续运行 30 分钟且满足 SLO，才能记录为最大可持续吞吐。

## 6. 结果批次

结果目录格式：

`docs/performance/stress/results/stress-YYYYMMDD-HHMMSS/`

未执行的项目必须明确标记为“未测”，不得伪造结果。
